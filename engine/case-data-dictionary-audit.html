The data-dictionary audit

What happened when we handed our own field definitions to three readers who could not see each other’s work — and, in one case, could not see anything but the definitions themselves. 23 July 2026.

← back to How we test

We ran a clean-room audit against our own data dictionary and led with the result rather than fixing it quietly, because a schema that shows what’s wrong with it is worth more than one that looks finished.

The three lenses — each able to fail differently

Three independent auditors, none seeing the others’ work.
lenswhat it was allowed to seewhat only it could catch
vs. codethe SQL, the CHECK constraints, and every script that writes a columndefinitions that claim what the code doesn’t do; columns defined but never written
cross-documentlexicon, decision journals, IRR reconciliations, design docsone term carrying two senses; a definition contradicted by a later lock
naive readeronly the definitions file — no code, no docs, no project briefanything only intelligible to someone who already knows the project

What it found — ~40 problems in 129 fields

Including two factual errors introduced that same evening. The most consequential:

Nothing in the engine tables is validated, and the schema never said so. coding_status was undefined on all seven tables — while being the field that carries the answer: 100% of 2,600 rows are engine-proposed; zero are cold-confirmed.
Two primary-key definitions were false. Written hours earlier from a single template, they claimed “one row per source text” for tables holding 12.25 and 10.00 rows per source.
A field wrong for the third consecutive time. perturbed_axis had already been hand-corrected twice; the audit showed it still listed three axes the CHECK constraint makes unstorable.
A self-contradiction. One definition was annotated “the draft hallucinated this vocabulary — wrong”; the definition two lines below still cited that same vocabulary.
Vocabularies controlled in intent, enforced nowhere. The Sitz fields pass LLM output through unvalidated — conforming by luck, not by constraint.

Why three lenses and not one

The naive reader caught that two fields were indistinguishable; the code lens caught why — they hold byte-identical values in all 1,817 rows. Neither alone gives you the fix. And where the researcher’s own walk, the naive reader, and the cross-document lens independently flagged the same two fields, that convergence is evidence the finding is real rather than one reader’s confusion.

The generalizable rule this produced

A verification marker must live in the code that changed, not in the data it displays. A check proposed during this round would have passed against the old build, because the strings it searched for were present in both. A check that cannot fail is not a check.

Where this sits among the tests — the pairing

This is a clean-room review: a finished artifact handed to readers who did not see the author’s framing. It answers is what we wrote true?

Its sibling is a clean-room implementation — the engine reproduction — which answers a harder question: can someone else rebuild the method from the written spec alone? A review can pass on a method that only its author can run. Only the implementation test can catch that.

Read together they bracket the claim: the dictionary audit checks the description, the engine reproduction checks the method.
