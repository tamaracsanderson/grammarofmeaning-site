The clean-room test

What happened when we gave the written specification to someone who had never seen the project, told them to build from it, and asked them to report where it ran out. 23–24 July 2026.

← back to How we test

We ran four independent audits and one clean-room implementation test against our own pipeline in a single night. The test halted at Engine 1.A — the stage that turns a text into moves. In diagnosing why, it found a live data bug in three of seven coded texts, and a parameter bug that had silently invalidated the temperature arm of every reliability study the project has run. Separately, a controlled re-run retracted our headline finding about the fan.

Why we ran it — the one test we described and had never performed

The project's claim is not here are some findings about religion. It is here is a method, and you can pick it up and run it. That claim has a test, and it was sitting on our own validation page, undone:

Clean-room implementation. Whether the method reproduces from its written spec alone, with no tacit knowledge. Its value is that it proves the method is not idiosyncratic — someone else can run it.

So an agent was given the specs, the corpus, and a target text it had never seen — the Parable of the Prodigal Son. It was told explicitly that “the method does not reproduce past stage X” would be the single most valuable result it could return, because a test that can only succeed is not a test.

An aside on Sol LeWitt

LeWitt wrote instructions and other people drew them. Wall Drawing #118 is a paragraph: place fifty points at random on any continuous stretch of wall, connect them all with straight lines. Draftsmen execute it; each execution looks different; the work survives being painted over and redrawn somewhere else. As he put it, the idea becomes a machine that makes the art. The certificate and the instructions are the work — the drawing on the wall is one instantiation of it.

That is exactly the shape of a clean-room test, and it is why the analogy is worth more than a flourish: the spec is the work, the execution is by someone else, and the divergence between executions is information rather than noise.

But the disanalogy is where the methodology actually lives. LeWitt declares his latitude — “any continuous stretch of wall,” “at random” — so variation between draftsmen is part of the work. Our spec had latitude too, and it was undeclared: three inputs that decide the quality of a coding run (the source key, which text to feed, what question to code against) turned out to be operator judgment calls that no document constrained. Undeclared latitude is not a work that encompasses its variations; it is an instrument that cannot tell you where its variance came from. The test's real finding is not that the pipeline broke — it is which of our freedoms we had never written down.

What it found — stage by stage

0.A Sitz✅ ran, wrote 1 row
0.B Paradigm✅ ran, wrote 9 rows — and gave us a free reliability read: run twice on identical input, the dominant paradigm reproduced exactly, relation_to_dominant agreed 8/8, but stance agreed only 5/8. The enforcement is on the wrong field: the stable one has no constraint, the unstable one does.
0.C Frame✅ ran, wrote 14 rows
1.A Grammar❌ two full runs, 33 minutes each, nothing written.
1.B → 2.xunreachable

The agent did not edit the engine to force it through. Its own words: “Making 1.A pass would have destroyed the result being measured.” That instinct is why the result is worth anything.

A wall-clock ceiling nobody could see

Two constants — a 2,000-character segment cap and a 300-second timeout — were mutually inconsistent, and neither was reachable from the command line:

   568 chars  (~12 moves)   ✅ succeeds
 1,985 chars  (~40 moves)   ❌ times out
 2,623 chars  (~50 moves)   ❌ times out

The segmenter was licensed to build work the timeout could not finish, and no configuration a faithful implementer could supply would make it pass. Worse, the timeout reported itself to the operator as EMPTY response (0 chars) — pointing at the model instead of at the clock, so a debugger would spend their time in the wrong place entirely.

There is a second layer. The “length-aware front door,” built in an earlier session specifically for this text — its own docstring names the Prodigal as the motivating case — never fired. It splits on blank lines; our corpus stores scripture one verse per line, with none. The fix was real, the text was the reason for it, and the corpus's own storage format defeated it.

A data bug, and a correction to our first account of it

The move-extractor's cross-segment renumbering read a key the model never emits, so on any text long enough to need more than one segment, local move-labels were never rewritten to global ones. Nine references dangled across three texts.

Our first diagnosis was wrong, and the data corrected it. We called it a rename artifact and said one text passed the integrity check while being wrong. Neither held. The nine references were multi-move extents crushed into a single-value column — one of them referenced a speech spanning sixteen moves. Fixing the column name alone would have kept the first and silently discarded fifteen correct observations. The repair stores the head and the full extent, and synthesises no edges, because an extent is a range and not a containment tree.

This matters more than the bug. A plausible, specific, mechanistic diagnosis is still fiction until you run the data — and ours was one more instance of exactly the failure mode this document is about.

A parameter accepted, propagated, printed — and deleted

del max_tokens, temperature   # not exposed by ClaudeAgentOptions v0.2.82

Every engine passes a temperature. None has ever applied one.

  • Every “temperature 0.0 determinism check” and every “temperature 0.7 independent sample” in the project ran at the same setting. The two arms of those studies were one condition.
  • The token-sizing logic of the length-aware front door is a no-op; the printed max_tokens was cosmetic.
  • It re-read results from the same evening: two comparisons we had described as temperature-0 determinism failures are ordinary sampling variance.

A parameter that is accepted, propagated, printed, and then discarded is worse than one that does not exist — because everything downstream reasons as though it worked.

What it did to the fan — two findings retracted

The control was false

The fan's method is hold everything, turn one frame-axis, see what world follows. The page said so, and the node panel printed OPERATION (WHAT IT DOES · HELD). It was held in 1 of 31 sibling sets. The prompt instructed the model to hold it; the response schema simultaneously invited it to emit a new one; it emitted a new one every time. Each branch changed the axis and the verb, so no difference between two branches could be attributed to the axis.

before  ·  after
operation held1 of 31  ·  25 of 25
content unique95.5%  ·  94.4%

The variation survived, and it is now attributable. Five branches from one parent, same verb throughout:

control →  grieve her, and let her go
E       →  do what the sign says: walk away
T       →  do not carry this alone; name what she did, so the next fellow is warned
S1      →  do not take the verdict; refuse it, and hold your ground
S2      →  ask what she is really angry about, and who taught her to call it hate

…which retracted our headline finding

Before the fix, the fan appeared to show that the axis selects the action — one axis produced walk away, another hold your ground, another dig underneath. It was the most interesting result we had. With the operation genuinely held, it collapsed: every axis now produces the same verb, because that is what “held” means. The signature was the uncontrolled variable moving.

A second retraction, the same night, by the same logic. We had recorded the fan as structurally reliable on the stability of its door-band bar rate. But door turned out to be perfectly confounded with one axis — 35 of 35 door nodes have it somewhere in their path — and the rate was stable at 100% under the old gate because the old gate's own rule barred every door node. The metric measured the gate, not the song, and did not survive the gate's revision (100% → 4.2%).

Both retractions have one shape: a result that was an artifact of the instrument, not a fact about the text. Neither was catchable by looking at output.

What is working — the parts that survived

  • Reading a single world end-to-end. Click a leaf and the fork, each depth's axis and value, the resulting line, and the rationale read back as a chain. Every auditor named this independently as the strongest thing on the page — it shows the reasoning, not just the output, which is what makes an interpretive move auditable.
  • The unit rule — a reporting move plus its nested content is one unit — verified correct against code and data.
  • The ripple — the transitive closure over the dependency graph is real computation, and it is what makes the seed non-random.
  • The question read-off — each unit's question is derived deterministically from the typed edge, not guessed. Called “the strongest link in the chain” by the code audit.
  • The fail-loud guards. When 1.A could not complete it wrote nothing and said so. No partial write, no silent success. That is why we have a clean result instead of a corrupted table.

What generalises — beyond this pipeline

(a) An instrument's failures are only visible from outside it. Every finding came from a reader who could not see the author's framing — an agent given only the definitions, only the code, only the live page. The audits that read our own explanations found far less.
(b) A check that cannot fail is not a check. Mid-session we proposed verifying a deploy by searching for a phrase present in both the old and new builds. It would have “confirmed” the new build against the old one. The rule: the discriminator must live in the code that changed, never in the data it displays.
(c) Silent degradation is the dominant failure mode. Six instances in one session: a constraint violation that fell back to a stale tree; a git stash that swallowed untracked work; a label truncated mid-word; a scheduled job installed but never loaded; a 0-byte database answering “no such table”; the corruption above. Every one produced a normal-looking result.
(d) Warnings must fire only on absences that are problems. Our schema flagged 16 fields as undefined; all 16 were primary keys. It flagged retired vocabulary for lacking definitions it should not have. Three false alarms train a reader to ignore the fourth — which is real.

The honest summary

We ran the one test our own methodology described and had never performed. It failed at stage 1.A, found a corruption affecting three of seven texts, invalidated a parameter every reliability study depended on, and cost us two findings we had recorded as results.

That is a good night, and the reason is worth saying plainly: the tree was clean that morning, and it was wrong. A demo that works proves nothing about a method. What we have now is an instrument that has been measured against itself, a list of what it gets wrong, and — for the first time — a reason to believe the parts that survived.
